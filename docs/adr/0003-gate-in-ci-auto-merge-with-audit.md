# The merge gate lives in CI, the reviewer is read-only, and auto-merge is on from day one

Every AFK pipeline we studied, sandcastle included, tells the agent to run tests and trusts that it did. Dex Horthy's evidence (his own lights-off outage, SlopCodeBench's 24% strict pass for Opus 5) and Huntley's placeholder warning say the same thing: an agent's "done" is a claim.

So the merge gate is required status checks on the PR: the target repo's own CI, a red-green proof (new tests must fail on main and pass on the branch), and a test-integrity check (no deleted, skipped, only, or todo tests). A separate fresh-context reviewer that never edits the branch ticks each acceptance criterion with evidence and emits a verdict as a required check. Merge is GitHub's native auto-merge plus merge queue, with no human and no LLM merger. Because the maintainer will not have a human merge path, the first 20 merges are each re-reviewed by an audit, with a revert PR on a miss. That audit runs on the model the maintainer configured for it, which should be the strongest the subscription serves: nothing ranks models, so the second opinion is better than the first only if the maintainer configures it to be.

## Considered options

- **Human at the PR boundary, calibrate, then flip.** The industry default. Rejected by the maintainer: with 50 PRs a month they will not read them, and unread human review is auto-merge in disguise.
- **Edit-in-place reviewer (sandcastle's).** Rejected: a reviewer that pushes commits is a second implementer nobody reviews, and GitHub will not let it approve its own changes.
- **LLM merger agent.** Rejected: GitHub's merge queue does the rebase and re-test deterministically; an agent is needed only for true conflicts, which escalate in v0.

## Consequences

- Review-and-fix still happens, inside the implementer run (Matt's standards-and-spec review, then Anthropic's bugs-and-simplification review with fix) before any PR exists. One polish pass, one judge, never recursive reviews.
- Human surfaces are exactly four: grilling specs, the escalation queue, the first-20 audit findings, the digest.
- Maintainability backpressure (complexity and duplication deltas) is deferred but expected; RL never penalises erosion, so the merge gate must.

## Amendments

### 2026-09-07: no merge queue on user-owned repos, v0 uses auto-merge plus update-branch

GitHub offers merge queues only on organization-owned repos (public, or private on Enterprise Cloud). factory-fixture and chronicle are user-owned, so the queue half of this decision cannot ship in v0. Moving the repos under an organization is #26; switching to the real queue once they are there is #27. Until then the merge path is:

- Auto-merge, squash, enabled by the implement workflow with FACTORY_PAT the moment the PR is created. GitHub refuses auto-merge on a draft (verified: `enablePullRequestAutoMerge` answers "Pull request is a draft"), so factory PRs open ready, not draft; the required `factory/verdict` status, absent until the reviewer posts it and `failure` on a fail, is what holds the merge. Auto-merge fires when every required check is green on the head.
- A ruleset named `factory` on the target's default branch, created by `scripts/onboard.sh`: a PR is required, squash is the only merge method, and `factory/verdict`, `factory/red-green`, `factory/test-integrity` plus the target's own CI checks must pass on a head that is up to date with the branch (strict). Repository admins bypass so a human can push the caller workflow; auto-merge never bypasses.
- Deterministic branch updating in place of the queue's rebase: on every push to main, and on a `repository_dispatch` (`factory-update-branch`) the review workflow sends with FACTORY_PAT after a passing `factory/verdict`, `update-branch.yml` calls GitHub's update-branch API with FACTORY_PAT for each open PR that has auto-merge enabled and is behind main. The merge commit is made by the PAT, so the target's CI and the merge gate run again on the new head, and auto-merge lands the PR on the latest main. The decision (which PRs to update) is a pure function with unit tests, `factory/update-branch/plan.ts`. No LLM anywhere in this path.
- The passing `factory/verdict` is carried from the old head to the new one by the same job, with its provenance in the status description. The reviewer judged the PR's diff against its ticket; merging main into the head leaves that diff as it was, and the checks that can change (tests) do re-run. The verdict that governs a head is the one on the head itself, else the one found by walking first parents through two-parent merge commits GitHub itself made (committer `web-flow`); the walk stops at the first commit a person or an agent pushed, so such a commit never inherits a verdict. A failing or pending verdict is never carried; a PR whose governing verdict is pending or failed is not updated until its re-review.
- A conflict the API cannot resolve gets a comment and `agent:blocked`; escalation proper is #16. Amended 2026-09-07 (#19): conflicts no longer escalate at once. Attempt 1 of the proof run stalled here: the two concurrent chain heads had each appended to the target's README, so with chains running side by side a README-style conflict is routine, not rare, and parking the PR kills the whole chain behind it. A conflict update-branch cannot resolve now hands the PR to the implementer (`agent:implement` on the PR, with FACTORY_PAT so `agent-implement-pr.yml` fires); implement-pr detects the conflict with `git merge-tree` against the local `main` and the agent merges `main` into the branch, resolves keeping both sides, tests, and commits; the push re-runs CI, the merge gate, and the review, and auto-merge lands the new head. Escalation happens only if that run fails, through the #16 retry path. The "LLM merger agent" rejection above stands for the routine case; true conflicts are exactly where it said an agent is needed. Corrected 2026-09-11 (#180): the hand-off is only for a PR the factory authored, per the 2026-09-10 amendment below. A conflict on any other PR gets the same comment plus `agent:blocked`, and no agent goes near the branch.

#### Consequences of the amendment

- Two PRs opened together both land: the first merges, its push to main triggers update-branch for the second, whose new head is re-tested and then merged. Each extra in-flight PR costs one more CI round per merge ahead of it, where a queue would batch; acceptable at the factory's v0 volume.
- The update happens in the target's workflow, so a target that does not carry the `push` and `repository_dispatch` triggers in its caller file stalls PRs behind main. `templates/factory.yml` has both.
- Commit statuses are always posted with GITHUB_TOKEN: the fine-grained FACTORY_PAT cannot write them (verified, 403), which also rules out a `status` event as the trigger.
- #27 removes the update-branch call, its triggers, and the verdict carry, and makes the three factory checks report on `merge_group`.

### 2026-09-07: the verdict walk trusts only merges the factory requested

GitHub also commits as `web-flow` when a person resolves a conflict in the web editor, and that merge changes the PR's diff. So update-branch posts a `factory/update-branch` status on the old head the moment its update call is accepted, and the first-parent walk crosses a GitHub merge only when the parent carries that marker. A walk that hits its hop limit reports `exhausted` and the PR is skipped with a request for a re-review, rather than being updated again with no verdict to carry.

### 2026-09-09: the audit's model is the maintainer's obligation, not a ranking (#118, #76 story 2)

The opening paragraph said the audit runs on the strongest configured model. Nothing computes that: `factory/lib/model.ts` resolves a model per role from a label or an input, and no ordering over model names exists anywhere in the tree. ### 2026-09-09: the merge gate checks only silenced tests; a deleted test is the reviewer's and the audit's to judge (#138)

The opening paragraph lists "no deleted, skipped, only, or todo tests" among the merge gate's checks. The deleted half is gone from the merge gate. `factory/test-integrity` fails only on a new `skip`, `only` or `todo` marker and lists deleted test files as information; `factory/red-green` reads the diff alone and passes vacuously, saying nothing was proved, when a diff deletes a source or test file and adds or changes no test; a deleted doc or config file removes nothing a test could have proved, so it excuses nothing. The reviewer prompt and the audit prompt each say the same one sentence: a deleted test is judged against what the ticket says it removes, wherever the ticket says it, and a deletion the ticket does not account for is a placeholder.

The reasoning. Both checks are required in the target's ruleset, so a wrong refusal on either has no judge after it: the retry told the implementer no test may be deleted, and only a human editing the ticket could clear it. That is what chronicle's ticket 296 met when its `## Removes` subject named two test files by role and the merge gate's word match found no word shared with `test/litellm-guards.test.mjs`. A wrong acceptance, by contrast, meets the reviewer, whose verdict is required, and the audit, which runs on every merge while the first 20 last. Two readers already own the judgment; the merge gate was a third that could not read. The `## Removes` convention itself had no counterpart in sandcastle, no ticket-writing skill emitted it, and it restated what a ticket's acceptance criteria already say, so it goes with the matcher: `factory/merge-gate/removes.ts` is deleted and nothing parses the section.

The read-only reviewer, the required verdict, the squash-only ruleset, the verdict carry and the first-20 audit all read as they did. The merge gate is still required status checks in CI, and still catches the placeholder shapes it can see in a diff: a source change with no test change, a test that passes on the base, a test that fails on the head, a silenced test.

### 2026-09-10: a conflicting PR is the implementer's, never a human's (#144)

The conflict bullet above hands a PR update-branch cannot bring up to date to the implementer. The retry handler had a second path to the same PR that ended somewhere else. GitHub does not start `pull_request` workflows on a conflicting PR, because it cannot build the trial merge those workflows run on, so the merge gate never posts on such a head. The retry handler's wait for the head's checks then ran out with nothing failed and nothing posted, and it labeled the PR `agent:blocked` for a human to re-label. `agent:blocked` is a handed-off label, so update-branch's conflict path skipped the PR and the reconciler parked it. Chronicle spec run #294 met this four times across three PRs in one slice of six tickets, each cleared by hand.

"Checks never posted" on a conflicting head is a fact about the merge, not about the ticket. So the retry handler now reads the PR's mergeability as GitHub reports it while it waits for the checks, ending the wait on a definite conflict and at the latest at its deadline (#145), and a definite conflict is handed to the implementer the way the conflict bullet already does it: a comment naming the cause, then `agent:implement` on the PR. No retry is spent and no `factory:retry-<n>` is added; the implementer's run merges the base into the branch, resolves, tests and pushes, and the push re-runs the merge gate and the review. A mergeability GitHub has not decided yet is never acted on; the PR is requeued as before. A failed check still outranks a pending one, so a conflicting PR with a real failure follows the failure.

`agent:blocked` keeps one meaning: a human must look. A deadline with no conflict and no failure still reaches it, because an unexplained head is exactly what a human should see. `HANDED_OFF_LABELS` and `PARKED_LABELS` are unchanged: with one meaning, parking a blocked PR is right. No decision this file records about the merge gate, the read-only reviewer, auto-merge or the audit changed; the "LLM merger agent" rejection stands, and a true conflict is still the one place it said an agent is needed.

### 2026-09-10: a requeue is never a human's either, on a PR as on a ticket (#148)

The amendment above says a deadline with no conflict and no failure still reaches `agent:blocked`. That is no longer true of a requeue. Which side a run is on used to decide what happened when it was rate limited on every account: a ticket-side run was requeued and the dispatcher picked it up, a PR-side run was labeled `agent:blocked` and waited for a person. A quota is nobody's failure and there is nothing for a person to do about one, so the escalation was work for a human that no human could clear, and it is what made removing the per-account cap (#149) look dangerous: mass rate limiting would have meant mass human queueing rather than mass waiting.

A requeue now means one thing on both sides: the comment naming the cause, no retry spent, and no label for a human. Each side is left in the state its own sweep reads, which is the whole of the difference. A ticket is left with no factory label, for the dispatcher. A PR is left in `agent:in-progress`, for the reconciler, which re-adds the start label at its `stuck_minutes` deadline: that is the one label it sweeps on a PR no run is on, so a requeue is the one way out of a run that keeps it rather than dropping it, and a PR with no `agent:*` label at all would be swept by nothing, which is worse than the `agent:blocked` this replaces. The PR then waits instead of queueing for a person at once. The reconciler is untouched, its tally included, so a requeue it re-dispatches is a stranding like any other and the second one escalates to `needs-human`: an outage still running two stuck deadlines later reaches a human through the rescue that was already there, rather than through the requeue itself. A re-dispatched run that only starts minutes after the sweep that asked for it resets that tally and loops instead, which is the shape per-account slot contention produced and #149 removes. Both requeue causes are covered, a rate limit and a head whose checks were still pending at the deadline, because they are one action in `factory/retry/retry.ts`. `agent-review.yml`'s own failure step tells a rate limit from anything else by the file the run script writes: that one gets the same requeue comment and no label, and a crashed reviewer or any other failure still gets `agent:blocked` and its comment.

So `agent:blocked` keeps its one meaning and is reached by fewer paths: only a failure a human can actually look at. `HANDED_OFF_LABELS` and `PARKED_LABELS` are still unchanged, and the reconciler, its stuck deadline and its rescue tally are untouched. No decision this file records about the merge gate, the read-only reviewer, auto-merge or the audit changed.

### 2026-09-10: the gate is named the merge gate, and the check names are left alone (#155)

`gate` was doing too much work. chronicle's own CI workflow is titled `CI Gate`, so on a target the bare word already meant two different things: the target's own checks and the factory's. The glossary's `Guard` entry shows the strain from the other side, and a harness-level egress control is a third thing the bare word would naturally cover. The maintainer hit this directly and could not tell from a sentence which one was meant.

This file's own name keeps `gate` deliberately: an ADR's filename is how every other document cites it, and its number is its identity, so renaming it would break references to buy nothing. The prose inside it moved.

So the concept is the **merge gate** now: `merge-gate.yml`, the `merge-gate:` job, `factory/merge-gate/`, `merge-gate.ts`, `merge-gate.json`, and the `merge-gate` failure kind and run role. `pr-merge` was considered and rejected: nothing in this workflow merges anything, GitHub's auto-merge and `update-branch.yml` do, so that name would have collided with the thing that actually merges.

The three status check names, `factory/verdict`, `factory/red-green` and `factory/test-integrity`, are byte-identical to before, deliberately. None of them contains the ambiguous word, so there was nothing to fix; the `factory/` prefix is what tells a maintainer which checks on their PR are the factory's rather than their own, and renaming them would have meant editing the ruleset on every target for no gain.

Two consequences worth recording:

- The retry marker comment writes `kind=merge-gate`, and its pattern was widened to accept a hyphen. A marker written before this change says `kind=gate`, which no longer parses, so its retry context is lost and the attempt reads as a fresh one. No compatibility shim was added: the factory was paused for the cutover with no factory PR in flight, so no such marker existed.
- The cutover is cross-repo, and its order is part of the decision. Each target's caller names the workflow by filename, so the rename breaks every caller the moment it reaches `main`. The sequence is therefore: stop the heartbeat and confirm no factory PR is in flight, land the rename, update both callers, restore the heartbeat, then prove the wiring with one ticket before real work resumes. Updating both callers is the maintainer's step. Corrected 2026-09-10 (#175): this read that a caller is a workflow file a fine-grained PAT generally cannot push, which is wrong. `FACTORY_PAT` carries `workflows` write (README step 2), and `docs/pipeline.md`'s list of what it cannot do names only commit statuses and repo variables. The step is the maintainer's for a different reason: mid-cutover every caller is broken, a broken caller posts none of the three checks, and a PR repairing one cannot be judged by the machinery it repairs. `templates/factory.yml` carries the new name for targets onboarded after this.

Nothing this ADR decides about the merge gate, auto-merge or the audit changed. The required checks, the read-only reviewer, the squash-only ruleset, the verdict carry and the first-20 audit all stand as they did.

### 2026-09-10: the merge gate runs each changed test file on its own (#151, #159)

The opening paragraph makes red-green "new tests must fail on main and pass on the branch". It did that by appending every changed test file to one invocation of the target's test command, per side. A batch's non-zero exit named every file in it, so one broken file dragged healthy ones into the failure message and the retry told the implementer to make passing tests pass. Each file now runs in its own invocation, on the base and on the head alike, and attribution comes free.

The batch's effective rule is kept deliberately: at least one changed test file must go red on the base, not all of them. A non-zero batch always meant one file, so this is the same meaning stated plainly, and requiring every file would newly refuse a PR that adds a real new test in one file and tidies the wording of another, which is correct work.

Two costs, both recorded in `docs/pipeline.md`. The test command's startup is paid once per file per side. And a test command that cannot run one file alone reports its own failure as the file's, which `go test` and pytest both do.

### 2026-09-10: a changed test the merge gate cannot run is passed over and named, not failed (#151, #160)

A changed test file the merge gate could not run is passed over rather than failed, named in the status with the reason, and left to the reviewer and the audit the way a deleted test is. Unrunnable means the file's process died before any test reported a result, which is different from a test that ran and failed, and until now the two were one non-zero exit. Such a file is left out of the base-red count, since it proved nothing either way, and a change whose touched test files are all unrunnable passes with a reason saying plainly that nothing was proved.

The false negative is preferred here for the third time, on the same reasoning as the deleted-test amendment above and for the same reason it was right there: both checks are required in the target's ruleset, so a refusal has no judge after it, while an acceptance meets the reviewer, whose verdict is required, and the audit, which runs on every merge while the first 20 last. What made this concrete: the merge gate knows one test command, so a browser test handed to `node --test` died on import and failed a PR whose implementation was correct. chronicle PR #320 met it, and the implementer diagnosed the limitation, reverted its browser test to main's content and moved the fix somewhere the merge gate would not look. An unwritten rule, "do not touch a browser test in a factory PR", was the alternative to this change, and it was already being paid for a run at a time.

**Detection is limited to the default test command**, deliberately. The merge gate chooses that invocation and can ask it for a structured report, so it can prove a file never ran. A command the caller supplied is never parsed: a wrong guess about output the merge gate does not understand would either hide a real failure or invent a fake excuse, and both are worse than the per-file split alone, which already stops the wrong blame. A target with two kinds of test can restore a real proof for both by giving the merge gate a test command that routes each file to the invocation its kind needs; that is the target's to write, and nothing about it is required.

The signal was verified by experiment rather than assumed, because the obvious guess was wrong. A file that crashes does not report zero tests: the report synthesises one entry named after the file, marks it failed, and attaches the dead process's exit status to it, while a genuine test failure carries the assertion and no exit status. Two things had to be true rather than one, though. That exit status is read at the failing entry's own level in the report, since a test failing over values with an `exitCode` field of their own prints one nested deeper; and no other entry may be a test result, since a file whose tests reported and whose process then died has run, and its exit is its own to answer for. Without the second, "the merge gate could not run it" would be a way through for a change nothing proved. Verified on Node 26 and cross-checked on Node 22; a report that carries none of this reads as having run, which fails the check as before rather than inventing an excuse.

What did not change: the required checks, the read-only reviewer, the squash-only ruleset, the verdict carry and the first-20 audit. Nor did the channel. The status text carries what was passed over, the same route the deleted-test amendment established, with no PR comment and no change to the reviewer's or the audit's prompt. A robot-written browser test can now merge with no red-green proof behind it, judged by the reviewer and the audit alone; that is the cost, and it is why a routing test command is not housekeeping.

### 2026-09-10: no unjudged merge path, rather than no human merge path (#175)

The opening paragraph gives the maintainer no human merge path, because at 50 PRs a month they will not read them and unread human review is auto-merge in disguise. That premise stands and the sentence is unchanged. What it was taken to mean does change: a PR the factory did not author had two outcomes, merged unjudged through the admin bypass or not merged, and the bypass was becoming the normal route for exactly the changes least able to afford it. chronicle #348 repointed a caller and #350 and #351 built the merge gate's own test routing; all three merged with no verdict on them, two by explicit bypass. The producers are also multiplying: interactive sessions now, cloud agents expected, and each opens a PR GitHub cannot tell from a person's. A cloud agent's PR carries less provenance than a factory PR, not more.

So the rule is no **unjudged** merge path. Any producer may ask for a verdict, and the answer to "who wrote this" stops deciding whether anything reads it.

**What a producer other than the factory does.** Push the branch to the target itself, open the PR with `Closes #N` in the body, label it `agent:review`, and arm auto-merge. The branch has to be in the target: `agent-review.yml` refuses a fork PR, taking `agent:review` back off and saying so, since `pull_request_target` runs with secrets and the factory never runs a fork's code. A fork PR also posts neither merge gate check, because `pull_request` from a fork holds a read-only token that cannot write a commit status. Nothing else is new: `factory/red-green`, `factory/test-integrity` and the target's own CI already run on any PR, with no label and the factory otherwise uninvolved (chronicle #349 is the demonstration). The reviewer judges the diff against that ticket's acceptance criteria and posts `factory/verdict` exactly as it does for a factory PR, from a context that never saw the code written. Auto-merge lands it on the same green checks a factory PR needs: the three factory ones and whatever the target's own CI posts. The bypass is not in this path.

**An unjudged merge is still possible, and only one way.** Through the admin bypass, which is now the exception rather than the second of two routes.

**A PR that closes no ticket has no judged path.** The reviewer ticks acceptance criteria; with no ticket there are none, so the verdict is a mechanical fail. That is today's behaviour, adopted rather than changed. Such a PR merges by bypass or not at all, and judging it against its own description was rejected: a PR body is the same claim as an agent's "done", and letting the thing under judgement write its own criteria is what this ADR exists to prevent.

**The bypass is kept, with one sanctioned use.** A repo whose caller cannot run posts none of the three checks, so a PR repairing that caller cannot be judged by the machinery it repairs. That is the one case with no other exit, and it is why the bypass cannot simply be removed. Narrowing it in the ruleset was considered and is not available: GitHub's bypass list names actors, not paths or conditions, so there is no way to say "admins may bypass, but only for the caller". Every other use is now a visible exception rather than a sanctioned route.

**`scripts/onboard.sh` is unchanged, and that is the finding.** The ruleset it writes was never the gap. `factory/verdict` is required on the branch, not on a class of author, so it already applied to every PR on every target; what was missing was any way for a non-factory PR to satisfy it. Nothing about the ruleset propagating to each new target needs to change, and a target already onboarded needs no re-run.

**The factory judges any PR and writes only to its own.** That is the rule this amendment adopts, and it is not yet what the code does: three writers reach a PR without asking who opened it, and each is a ticket below. Judging is read-only, so extending it costs nothing. Writing is not, and the line falls in the same place every time: bringing a branch up to date when main moves is a deterministic API call and applies to any PR with auto-merge armed, while anything that puts an agent on the branch, or closes the PR, applies only to a PR the factory authored. Corrected 2026-09-11 (#195): "not yet what the code does" was status, and it has lapsed. All three writers ask who authored the PR now, and the 2026-09-11 amendment below states the rule with the status taken out of it.

#### Consequences of the amendment

- **Nobody may be told to use this path until #174, #180 and #183 land.** Escalation strips a PR's `agent:*` labels and closes it, which is right for a factory PR because the ticket still holds the work and a later run rebuilds it. Applied to a PR the factory did not author it closes a PR no later run will reopen, and while the branch is kept the PR, its review and its place in the queue are not. The route is reached without anyone intending it: a PR closing no ticket fails its verdict for want of criteria, `unretryableReason` correctly reads that as unretryable since no implementer run could ever pass it, and `decide` turns unretryable into an escalation that closes the PR. So labelling such a PR `agent:review`, the one action this amendment asks a producer to take, destroys it. The decision is recorded now because it is sound now; #181, which carries the instruction into every target's `AGENTS.md`, is blocked on all three for exactly this reason. Corrected 2026-09-11 (#195): this bullet held a rule and its status in one clause, and the status has lapsed, since #174, #180 and #183 are all closed. As a bar on *telling* producers, it also missed a PR nobody was told to label (#182). The 2026-09-11 amendment below restates the rule with no condition that can be met, and the reason given above for it stands.
- **Arming auto-merge enrols a PR in `update-branch`.** `planUpdate` gates on `autoMerge` alone and never asks who opened the PR, so a PR the factory did not author is kept current with main from the moment it is armed. This is required rather than incidental: the ruleset is strict, so a head behind main cannot merge, and without it such a PR, once armed, would stall the first time main moved.
- **The conflict hand-off has to narrow.** `planConflict` hands any conflicting PR not already held by a label to `implement-pr`. On a PR the factory did not author that is an agent rewriting someone else's branch, so a conflict there goes back to its author instead. Ticket: #180.
- **So does the retry hand-off, and it is the common path.** A verdict that fails for a real reason, criteria present and not all ticked, never reaches `unretryableReason`: `decide` returns `retry`, and `retry` in `factory/retry/retry.ts` labels whatever `actOn` names, which is the open PR whenever there is one. So `agent-implement-pr.yml` runs on the producer's branch and pushes to it, and a second failure escalates. The conflict path in the same file hands off the same way. A failed verdict does not go back to its author today; making it do so is the point. Ticket: #183.
- **The reviewer's trust policy has a hole this path widens.** `fetchPullRequestContext` fetches the linked ticket without its author and puts the body in the prompt as the acceptance criteria; comments are filtered, the body is not. The dispatcher's author check was the only thing covering it, and the judged path is a second route that skips the dispatcher. chronicle is public with issues enabled, so anyone can file the ticket a PR points at. The reviewer and the audit are read-only, so the exposure is a verdict talked into passing rather than code execution, but a verdict is a required check. Ticket: #179, and it is a pre-existing hole rather than one this decision creates: hand-labelling `agent:implement` already reaches an untrusted body.
- **The convention against closing keywords narrows.** `docs/agents/issue-tracker.md` forbids `Closes #N` in a PR body outright, because the dispatcher then skips that ticket. The reviewer finds a PR's ticket only by that keyword, so the judged path requires it. The two only conflict when the factory is meant to build the ticket; when the PR's author is doing the work, the dispatcher standing down is correct. Ticket: #181, which also carries the instruction every target's `AGENTS.md` needs.
- **Availability, not automation.** The judged path works when a producer knows to label, and does nothing otherwise. That is a convention, and it fails closed: a producer that forgets gets a PR that sits blocked, which is the status quo rather than a regression. Nothing merges unjudged for want of a label. Making it automatic, by having the reconciler label any unjudged PR, was considered and deferred to #182 until a producer that ignores the instruction files actually exists. Corrected 2026-09-11 (#195): the deferral stands. What makes automatic labelling safe when #182 builds it is the same rule a producer's own label is held to, stated in the 2026-09-11 amendment below: every write that can follow the label asks `isFactoryAuthoredPr`, and none of them asks how the label got there.
- **The automation that does exist inherits the heartbeat.** `update-branch` and the reconciler run on the sweep, which is driven by a launchd job on the maintainer's machine every 10 minutes; GitHub's own cron is the fallback and fired 6 times against about 129 expected over 21 and a half hours. So a judged PR is kept current with main only while that machine is awake.
- **A judged PR the factory did not author becomes a factory PR.** The reviewer writes its verdict section into the body, which is one of the three things `factory/lib/factory-pr.ts` tests. This is wanted: it is what puts the PR in front of the first-20 audit. It also means the reconciler adopts it, re-arming auto-merge and re-requesting review on a head with no verdict.
- **The judged path costs a reviewer run per PR.** One subscription run and its latency before the merge, on work an interactive session has already reviewed before opening the PR. What the verdict buys over that session's own review is a reader that never saw the code written, and a result GitHub can gate on.

No decision this file records changed. Both the "human at the PR boundary" and "LLM merger agent" rejections stand: this amendment removes neither a human nor a judge, it removes the unjudged merge.

### 2026-09-11: the factory asks who authored a PR before it closes it or puts the implementer on it (#195)

The amendment above adopted "the factory judges any PR and writes only to its own", then held the code to it with a ban that could expire: nobody may be told to use the judged path until #174, #180 and #183 land. That one clause carried two things. The rule is permanently true, while where the code honoured it was status that changed three times in a day. The clause failed both ways on 2026-09-11. As a bar on *telling*, it read as binding the ticket that tells producers (#181) and not the one that labels PRs with nobody told (#182): two sessions read it that way, one removed two of #181's three blocking edges, and the other concluded #182 had nothing blocking it. And once #183 closed, it was a present-tense ban that no longer bound anything, and only checking three ticket states could reveal that.

So the rule is anchored to the predicate that already answers the question, and the status sits beside it, dated.

**The rule.** Every factory action that closes a pull request, or puts the implementer on its branch, asks `isFactoryAuthoredPr` first. The predicate and its contract live in `factory/lib/factory-pr.ts`: `isFactoryAuthoredPr` is what the factory may *do to* a branch, and `isFactoryPr` is what it reads and judges. The implementer is the agent that commits to a branch, which is what the amendment above meant by putting an agent on one. The reviewer is read-only on the branch, so labelling a PR for review is not one of these writes. The rule names no ticket and has no condition that can be met, and a write path built later owes it exactly what the existing ones do.

**It binds the write, not the instruction.** How a PR got onto the judged path does not enter into it. A producer's own `agent:review`, a person's, and a reconciler labelling any unjudged PR automatically all lead to the same writes, and each of those asks. So an automatic route onto the path, #182's included, is covered by the rule as it stands and needs no wording of its own.

**It is about asking, not about the answer.** What a site does once it knows is that site's decision, and the sites do not agree on it, nor do they need to. What each owes the rule is that the question comes before the write.

**Bringing a branch up to date is not one of these writes,** by the line the amendment above drew and this one keeps. `planUpdate` has update-branch merge the base into any PR with auto-merge armed and asks nothing about authorship: that is GitHub's API making the merge, no agent is on the branch, and the strict ruleset would otherwise stall an armed PR the first time main moved.

#### Where the factory asks, as of 2026-09-11

Three sites, each calling the one predicate:

- `prEscalation` in `factory/retry/escalation.ts`, from #174, closed 2026-09-11. Escalation closes a **Factory-authored PR**. It leaves any other PR open with `needs-human` on, and the retry handler disarms its auto-merge.
- `planConflict` in `factory/update-branch/plan.ts`, from #180, closed 2026-09-11. A conflict update-branch finds is a hand-off, `agent:implement`, on a Factory-authored PR, and a tell-author, `agent:blocked`, on any other.
- `prFix` in `factory/retry/escalation.ts`, from #183, closed 2026-09-11 and landed as `cb9cbfc`. The retry handler takes it for both of the times it would put the implementer on a PR: the retry after a failed check, and the hand-off of a conflict it finds while waiting for checks. On a Factory-authored PR either goes ahead with `agent:implement`. On any other, either is a tell-author with `agent:blocked`.

That is two vocabularies across three sites. #183 took #180's words rather than inventing a third set, and escalation keeps `needs-human` apart from `agent:blocked` because ADR 0005 makes them different labels. The difference is why the rule is stated as asking.

As of this date the reconciler is not a site either. On a PR stuck in `agent:implement`, it re-adds that same label, which repeats a decision already made and makes no new one. The factory adds `agent:implement` to a PR only through `planConflict` and `prFix`, which both ask, so a PR stuck there got the label from one of them or from a person.

The condition the amendment above set is met by its own terms. Telling a producer to take the judged path is #181's to do.

#### The test, and how far to trust it

`factory/lib/branch-writes.test.ts` holds a table of the sites and of the module that makes each site's write: `factory/retry/retry.ts` for the first two, `factory/update-branch/update-branch.ts` for the third. For each site it checks three things:

- the answer turns on who authored the PR;
- the site calls `isFactoryAuthoredPr`, imported from `factory/lib/factory-pr.ts`, rather than a copy of its two arms;
- the writing module calls the site.

In both directions, it also checks that the table names every call to the predicate under `factory/`. Each site's answers are compared only with that site's own, never with another site's, since they do not share one.

It pins the sites that exist. It fails on these:

- a tabled site that stops asking, or asks something else;
- a writing module that stops calling its site, which is what reverting #183's change to `retry.ts` does;
- a new site that asks without being tabled.

It does not see which of a writing module's functions call the site, or what they do with the answer. A new write path that calls neither the predicate nor a site is invisible to it, because a call is what it looks for. That is why the contract stays in `factory-pr.ts`'s doc comment, which is what the author of a new write path reads, and why this rule points at the predicate rather than restating its arms.

No decision this file records changed. The line the amendment above drew, judging any PR and writing only to the factory's own while keeping any armed PR current, stands where it was drawn. What changed is what the rule is anchored to, and that a test now holds the existing sites to it. The three sentences above that carried the lapsed status are corrected in place, with their original wording kept.
