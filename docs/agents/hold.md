# Holding a ticket back

`hold` is how you say "ready, but not yet" to the factory. It is not one of the five triage roles in `triage-labels.md` and no skill applies it; a human adds it and a human takes it off.

The hold has a page of its own rather than a section in `triage-labels.md` because that page is vendored verbatim: `factory/plugins/README.md` keeps it byte-identical to the `setup-matt-pocock-skills` copy so a re-run of the skill is a no-op and a bump can re-copy it, and only the right-hand column of its table may be edited. Prose added there is prose the next bump silently deletes.

- **Nothing that decides to start an agent starts one on a ticket carrying it**, whatever else the ticket says. `hold` + `ready-for-agent` is a legitimate pair and reads as one: the ticket is finished, and somebody is holding it. Three deciders read it (#185): the dispatcher never dispatches the ticket, the retry handler stands down instead of retrying a failed attempt, and the reconciler leaves a stuck ticket alone instead of re-adding its start label, and leaves a held PR's merge path alone too, re-arming and updating nothing. The last two read it on the ticket's open PR as well, and on the ticket when they are looking at its PR, so holding the ticket holds the work in flight on it. Two places still hand work on without reading it, under "What it does not stop" below.
- **It works on a ticket already in flight, and it is how to stop one.** Add `hold`, then cancel the run if you want it stopped now. A run in progress is not interrupted by the label, and one that goes on to succeed hands its PR to the reviewer as usual; what the hold stops is everything the factory decides after a run fails or strands. Cancelling without `hold` still gets one replacement run, because a cancel reads the same as a `timeout-minutes` kill and that kill keeps its retry (#51). When the retry handler stands down it spends no retry, adds no `needs-human`, takes no `agent:*` label off, and comments on the held ticket or PR naming the label that stopped it.
- **Removing it is the whole release; nothing else has to be done to the ticket.** How soon is the sweep's, not the label's, and which sweep depends on where the ticket was. One that never started, or whose attempt the retry handler stood down on, carries no `agent:*` label and is the dispatcher's: taking `hold` off fires `issues: unlabeled`, which wakes the dispatcher at once on a target whose caller subscribes to that action (`hold` is unprefixed, so it is outside the `agent:*` and `factory:*` namespaces a caller drops the removals of), and a target being sent `factory-sweep` every 10 minutes catches it within that interval if the event is lost. Ten minutes is the heartbeat's interval, not a guarantee GitHub makes and not a promise on a target nobody sends the heartbeat to, where it is whenever the caller's `schedule` next fires; `docs/pipeline.md` has the measurements and the trigger set a target can have drifted off.
- **Work still carrying a state label resumes through the reconciler, and not at once.** A PR the retry handler stood down on is kept in `agent:in-progress`, and a ticket held while its start label was still on keeps that label. The dispatcher will not take either, since the factory already holds them, so the `unlabeled` wake does nothing for them; the reconciler re-adds the start label on its first sweep past the stuck deadline (`stuck_minutes`, 15 by default). That deadline runs from when the start label went on, not from when the hold came off, so work held for longer than it resumes on the next sweep, within the heartbeat's 10 minutes, and work held for less waits out the rest of it. That resume is a re-dispatch like any other and counts as the reconciler's first miss on it, as a requeue's does, so a second lost event after it escalates.
- **What it does not stop.** Two hand-offs do not read it yet:
  - an agent workflow's own success step. An implementer run that succeeds labels its PR `agent:review` (implement and implement-pr alike), so the reviewer starts on a held ticket's PR whose run was already going when the hold landed. Cancel the run to stop that.
  - update-branch's conflict hand-off. A held PR the factory authored, with auto-merge armed, carrying no `agent:*` label and conflicting with `main`, is still handed to the implementer, and so is one whose ticket is held. One the retry handler stood down on keeps `agent:in-progress` and is skipped there, so the gap is a held PR between stages.

  Nor does it disarm auto-merge already armed, so a PR whose checks are all green can still merge while held.
- **`hold` is not `needs-triage`.** `needs-triage` means nobody has decided yet. Reach for `hold` when the decision is made and the answer is "not now", so that a triage pass reading `needs-triage` + `ready-for-agent` never has to guess which of the two somebody meant. That guess is what #169 is about: on chronicle a pass read the pair as drift on 14 tickets, cleared it, and released 12 into the factory at once.

The full hold set (`hold`, `ready-for-human`, `needs-triage`) is `HOLD_LABELS` in `factory/lib/labels.ts`, and the dispatcher, the retry handler and the reconciler all read it from there. The last two are a backstop and not the way to hold something: given correct labelling neither can fire, since the dispatcher only looks at tickets carrying `ready-for-agent` and neither of those belongs on one, nor on a PR. They stay in the set so that tickets already held by the old `needs-triage` pair keep being held, with no window in which one is unprotected. The flip side since #185 is that either one on a ticket or PR the factory is already working on stops it as `hold` would, so a target whose own automation labels PRs `needs-triage` holds every factory PR it touches.

## These labels are notes here, and orders on a target

This repo carries no caller, so no dispatcher reads its labels: `ready-for-agent` here is a note between a maintainer and an interactive session. On a target repo the same label is a dispatch order.

So the hazard lands on the day a repo becomes a target, not on the day someone applies a label: the whole backlog arms at once, without anyone having relabelled anything. Sweeping it before the caller lands belongs to whoever adds the caller, and `docs/pipeline.md`'s onboarding details say what that sweep is.
